# Migrations

Strategy: **versioned Drizzle migrations** in `lib/db/drizzle/`, applied with
`drizzle-kit migrate`. `drizzle-kit push` is kept only for throwaway local
experiments and must not be used on shared or production databases.

## Commands

```bash
# apply all pending migrations (new or existing environment)
DATABASE_URL=<conn> pnpm --filter @workspace/db run migrate

# after changing lib/db/src/schema/*: create a new migration, review the SQL, commit it
DATABASE_URL=<conn> pnpm --filter @workspace/db run generate --name <short_name>
```

Applied migrations are tracked in `drizzle.__drizzle_migrations`.

## Baseline (`0000_baseline.sql`)

Contains the Phase 1 + Phase 2 schema (`topics`, `users`, enums, indexes).
It was generated by drizzle-kit and then hand-edited to be **idempotent**
(`CREATE TYPE` wrapped in `DO ... duplicate_object`, `IF NOT EXISTS` on tables
and indexes). Therefore:

- Empty database: creates everything.
- Database previously initialised with `drizzle-kit push` (the Replit dev DB):
  creates nothing, keeps all data, records the baseline as applied.

Assumption: an existing push-initialised database matches the current schema
(true for the Replit dev DB as of Phase 2). If columns differ, `IF NOT EXISTS`
will not repair them — compare with `drizzle-kit push --strict` (dry review)
before migrating.

Verified 2026-10-01 on PostgreSQL in the sandbox: empty DB → migrate OK; push DB
with an existing user → migrate OK, user preserved, 1 migration recorded;
re-running migrate is a no-op.

Rules: never edit an applied migration (except this one-time baseline edit),
never delete migrations, never reset shared databases.
